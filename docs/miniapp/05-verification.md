## 二、真实服务联调

后端在本机启动（独立端口），用真实的智能提示与公开访问令牌请求接口。

| 请求 | 结果 |
| --- | --- |
| 登录（携带真实 scene） | 返回令牌、访客标识、智能提示标识与名称，`dev_mode` 为 `true` |
| 取资料（携带访客令牌） | 返回智能提示名称、开场白与对话轮数 |
| 创建会话 | 返回会话标识 |
| 提问（携带访客令牌） | 约 5 秒返回完整回答，`timeout` 为 `false`，带本轮记录标识 |
| 中文问题 | 问题与回答均正确保存，无乱码 |
| 无效 scene 登录 | 返回「小程序码无效，或该智能提示已停止对外访问」 |
| 不带令牌访问资料 | HTTP 401 |
| 不带令牌生成小程序码 | HTTP 401 |
| 用访客令牌生成小程序码 | HTTP 403 |
| 用其他访客的会话标识提问 | 返回「无权访问该会话」 |

数据库核对：两次提问都在聊天记录表里写入了问题、回答与回答 token 数，说明一次性返回的通道与网页分享页共用同一套落库流程。

## 三、浏览器实测（管理端页面）

后端与本机前端开发服务器同时启动，在浏览器里点击验证小程序码页面。由于本机没有真实小程序凭据，用一个符合微信接口返回格式的本地桩服务顶替微信开放接口，其余代码路径完全一致。

| 操作 | 结果 |
| --- | --- |
| 打开应用概览 | 侧边栏与概览按钮都出现「小程序码」入口 |
| 未配置微信凭据时打开小程序码页面 | 页面显示服务端返回的原因「未配置微信小程序凭据，无法生成小程序码」 |
| 配置凭据（指向桩服务）后重新生成 | 页面渲染出接口返回的图片，并列出智能提示、scene、页面、环境四项信息 |
| 切换运行环境为正式版 | 请求参数随之变化，仍正常返回 |
| 用访客令牌请求管理端小程序码接口 | HTTP 403 |
| 无效 `env_version` | HTTP 400，响应体是带原因的 JSON |
| 管理端调用微信登录接口（携带 code） | 返回令牌，`dev_mode` 为 `false`，说明走的是微信换用户标识分支 |

前端在这一步暴露并修掉了一个真实问题：管理端请求层默认只认 `code` 为 200 的响应，而小程序接口按约定使用 `code` 为 1 的统一响应体，导致生成成功也会被判为失败。处理方式是把小程序码请求标为静默，由接口封装自行判断成功与失败，失败原因取服务端的 `msg`。

## 四、过程中修掉的问题

| 问题 | 原因 | 处理 |
| --- | --- | --- |
| scene 查询报 `operator does not exist: bigint = character varying` | 公开访问令牌是数字列，直接按字符串比较时数据库无法使用索引 | 先把 scene 转成长整型并做合法性校验，再参与查询 |
| 聊天服务出现同名方法歧义 | 新增的通道参数与原连接参数重载后，`null` 实参无法确定调用哪一个 | 只保留一个入口，由调用方显式传入通道实现 |
| 参数校验异常缺少统一响应 | 全局异常处理器只回显消息，没有区分参数问题 | 在全局异常处理器里单独识别参数校验异常并返回 400 |

## 六、本机联调环境的两点限制

### 1. 流式回答经过前端开发服务器代理时收不到数据（已定位并修复）

**现象**：网页分享页提问后一直停在「Generating Response...」，接口最终返回 0 字节。

**排查过程**：用字节级中转把后端真正写到线上的字节抓下来对比。

| 场景 | 结果 |
| --- | --- |
| 直连后端（客户端默认长连接） | 6 秒内返回全部分片，响应头 `transfer-encoding:chunked`，正文以 `47\r\n...\r\n0\r\n\r\n` 正确分块 |
| 直连后端但显式带 `Connection: close` | 只有响应头，正文一个字节都没有 |
| 经开发服务器代理 | 代理发给后端的是 `Connection: close`，于是同样只有响应头 |

**结论**：分片封装没有问题。根因是请求头带 `Connection: close` 时，框架的 `prepareConnection()` 会把已经由 `addServerSentEventsHeader()` 标记成长连接的流式响应重新改成关闭，传输层写完响应头就断链，后续 SSE 分片全部写入已关闭的通道（日志表现为 `cancel send data ... closed:true`）。

**修复**（两处，均已落地）：

- 框架侧：`prepareConnection()` 判断关闭时对已标记为流式的响应忽略客户端的关闭要求，流式响应结束时仍由应用关闭连接。补丁源码在框架的 HTTP 公共模块，说明见框架文档 `sse-connection.md`，回归测试 3 项通过。**已安装到本机 Maven 仓库**（同一版本号、内容为补丁版本；已确认其他 jar 未内嵌该类，不存在覆盖顺序问题）。实测：客户端带 `Connection: close` 时，流式响应头为 `connection:keep-alive` 且分片正常送达；普通响应仍按 `close` 处理。
- 前端侧：开发服务器代理对 `/chat_message/` 路径向上游发送长连接，未打补丁的后端也能正常流式返回。实测：首字节 0.50 秒、5.0 秒收到 10.2KB 完整流。

**关闭时序**（字节抓包）：回答结束时业务调用 `SseEmitter.closeChunkConnection`，先写 `0\r\n\r\n` 结束块，再由后端主动关闭连接（`0\r\n\r\n` → `BACKEND-FIN` → `CLIENT-FIN`）；生成期间连接一直保持。

**浏览器验收**（使用已安装的框架包、清空本地存储后以全新访客进入）：提问后界面出现流式状态，完整回答与检索过程渲染完成，无卡住、无报错。

**部署提醒**：反向代理同样要让 SSE 走 HTTP/1.1 且保持上游长连接（例如 nginx 的 `proxy_http_version 1.1;` 与 `proxy_set_header Connection "";`），并把读超时调到大于最长回答时间；响应已带 `X-Accel-Buffering: no`。

### 2. 跨域直连后端的预检不稳定

预检对部分路由返回 204 但不带跨域头，对另一部分路由返回 404。小程序不受影响（小程序请求没有浏览器同源限制）；网页端在本机联调时保持默认的相对地址与代理模式即可。
